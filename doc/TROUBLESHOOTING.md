## 1. Build and tooling

### `Value '…' given for org.gradle.java.home Gradle property is invalid`

`gradle.properties` contains `org.gradle.java.home`, which points to the JDK of a developer machine. On
another machine or in a container, this path does not exist.

- Override it on the command line: `./gradlew build -Dorg.gradle.java.home="$JAVA_HOME"`. The CI workflow
  and `backend/Dockerfile` do this.
- Or set your own JDK in `~/.gradle/gradle.properties`.

### Gradle fails with a recent JDK (25+)

Gradle 9.0 (the wrapper version) does not run on Java 25. Point `org.gradle.java.home` to a JDK between
21 and 24.

### `Cannot find name 'PageProps'` / `'LayoutProps'` (frontend)

These global types are generated by Next.js and do not exist in a fresh clone. `npm run typecheck` already
runs `next typegen` first. If you call `tsc` directly, run `npx next typegen` before it.

### `npm audit` reports vulnerabilities

They are in the development tooling (ESLint dependencies), not in the production bundle. Check with
`npm audit --omit=dev`, which should report none.

## 2. Login (OpenID Connect)

### HTTP 500 on `/oauth2/authorization/oidc`

The identity provider is unreachable. Its configuration is only fetched at the first login, so the
application starts without it.

- In development: `docker compose up -d keycloak`, then check
  `http://localhost:8180/realms/jtypo/.well-known/openid-configuration`.
- Otherwise: check `OIDC_ISSUER_URI`.

### Keycloak shows "Invalid parameter: redirect_uri"

The backend builds the return URL from the request, and the provider only accepts registered URLs. The
development realm (`deploy/keycloak/jtypo-realm.json`) accepts:

- `http://localhost:3000/login/oauth2/code/oidc`
- `http://localhost:3001/login/oauth2/code/oidc`
- `http://localhost:8081/login/oauth2/code/oidc`
- `http://localhost/login/oauth2/code/oidc`

Common causes:

- **Wrong address**: the frontend was opened with the machine IP address (`http://192.168.x.x:3000`)
  instead of `localhost`.
- **Port 3000 taken**: the frontend runs on another port. Use 3001, or add the port to the realm and
  recreate the Keycloak container, because the realm is imported only once.
- **Wrong port in the return URL**: the backend was started without `FORWARD_HEADERS_STRATEGY=framework`,
  so it builds `localhost:8081` instead of the frontend port.
- **Production**: register `https://<site>/login/oauth2/code/oidc` with your provider.

### Keycloak error "Missing parameter: code_challenge_method"

The provider requires PKCE. The backend always sends it (`code_challenge_method=S256`). If you still see
this error, an older backend is running: rebuild it and restart it.

### The login page comes back with "Login failed"

After a refusal, the provider redirects to `/app?loginError=1`. The Keycloak logs give the reason:

```bash
docker logs <keycloak container> 2>&1 | grep LOGIN_ERROR
```

Before this behaviour existed, a refusal made the browser loop between the application and the provider.

### Logged in, but the next request is anonymous again

`SESSION_COOKIE_SECURE=true` (the default in the `api` image) makes the browser send the session cookie
over HTTPS only. Serve the site over HTTPS. For a local test over plain HTTP, set
`SESSION_COOKIE_SECURE=false`.

## 3. API errors

| Status | Meaning | What to do |
|--------|---------|------------|
| 401 | No valid session (web mode) | Log in. The API never redirects to the login page. |
| 403 on `POST` / `DELETE` | CSRF token missing or wrong | Send the value of the `XSRF-TOKEN` cookie in the `X-XSRF-TOKEN` header. The cookie is set by any API response, e.g. `GET /api/me`. |
| 403 on `/api/scans/{id}` | The scan belongs to another user | Expected. |
| 404 on `/api/generate-and-check`, `/api/cancel`, `/api/data/**` | Desktop endpoints, loaded only in local mode | Use `/api/scans`. |
| 404 on `/api/screenshots/{hash}` | None of your scans contains this screenshot | Expected. |
| 409 on `DELETE /api/scans/{id}` | The scan is already finished | Nothing to cancel. |
| 429 | Rate limit (120 requests per minute) or scan quota (2 simultaneous scans, 50 per 24 hours) | Wait for the number of seconds in `Retry-After`. Limits: `jtypo.rate-limit.*`, `jtypo.quota.*`. |

## 4. Live results (SSE)

### No results arrive, but the scan progresses

A proxy is buffering the stream.

- **The backend side** is already handled: it sends `Cache-Control: no-cache, no-transform` and
  `X-Accel-Buffering: no`.
- **Your own nginx**: check `proxy_buffering off` and a long `proxy_read_timeout` on
  `/api/scans/{id}/events`, as in `deploy/nginx/jtyposquatting.conf`.
- **Compression**: disable it on `text/event-stream`.
- **Next.js development server**: it closes a proxied connection after 30 s without data. The backend
  sends a keep-alive comment every 15 s.

### The stream stops after 30 minutes

This is expected: `jtypo.sse.max-duration-ms` limits each stream to 30 minutes. The browser reconnects by
itself with `Last-Event-ID` and only receives the results it missed.

### `Failed to proxy … socket hang up` in the Next.js development server

This is transient: a request reused a connection that had just been closed (for example, a stream
interrupted on the client side). Retry the request. It does not happen behind nginx.

### The same result appears twice

This was a frontend defect, now fixed: results are de-duplicated by id. If you see it again, report the
browser and the steps to reproduce.

## 5. Scans and checks

### A scan stays `PENDING`

No worker is running.

- `jtypo.worker.enabled=false` disables the worker. The `api` profile and the test profile set it.
- In a deployment, start at least one instance with `SPRING_PROFILES_ACTIVE=worker`.
- The `JTypoNoWorkerProcessing` alert (`deploy/prometheus/alerts.yml`) detects this situation.

### A scan stays `RUNNING` after a worker crash

Another worker takes it over once its heartbeat is older than `jtypo.worker.stale-after-ms` (2 minutes).
The domains already checked are not checked again.

### Every domain is unreachable

- **No outbound access**: check that the worker can resolve DNS and reach the Internet on ports 80 and 443.
- **Blocked destination**: the anti-SSRF policy blocks every private, reserved or loopback address. Look for
  `Blocked outbound connection` in the logs. To test against a local server only, set
  `jtypo.outbound.allow-private-addresses=true` and `jtypo.outbound.allowed-ports=`. Never do this on a
  public deployment.

### Fewer domains than expected

- Domains checked less than 24 hours ago are taken from the cache. Use `forceRefresh` ("Ignore the cache")
  to check them again.
- A scan checks at most `jtypo.quota.max-domains-per-scan` domains (50 000).
- Generated names that are not valid domain names are discarded.

### Scans are slow

- A scan checks thousands of domains, with at most `jtypo.analysis.max-concurrent-checks` (64) at the same
  time per worker.
- Each check has a 3 s connect timeout and a 10 s read timeout.
- Add workers, or raise the limit, while staying polite with the target hosts.

## 6. Screenshots

### No screenshot at all

Headless Chromium is not installed. Look for `Screenshots disabled: Chromium could not be started` in the
logs, then install it:

```bash
./gradlew :backend:installPlaywrightBrowsers           # development machine
./gradlew :backend:installPlaywrightBrowsers -PwithDeps   # also the system libraries (CI, needs sudo)
```

In containers, the `worker` image already contains Chromium.

### Chromium fails to start because of its sandbox

The Chromium sandbox needs unprivileged user namespaces. These are disabled on some systems, such as
Ubuntu 24.04 with AppArmor, and in containers.

- Inside an isolated container, set `jtypo.screenshot.chromium-sandbox=false`
  (`JTYPO_SCREENSHOT_CHROMIUM_SANDBOX=false`): the container is the sandbox.
- Keep the sandbox enabled anywhere else.

### Some online domains have no screenshot

This is expected in the following cases:

- the response was not 2xx;
- the page has fewer than 5 characters of text;
- the capture took longer than `jtypo.screenshot.timeout-ms` (15 s);
- every browser was busy (`jtypo.screenshot.max-concurrent`, 2 per instance);
- the page targeted a forbidden destination.

The metric `jtypo_screenshots_total{outcome}` counts screenshots that succeed, fail or are blocked.

## 7. Tests

### Testcontainers tests are skipped, or fail with rootless Podman

Testcontainers needs a Docker-compatible API. With rootless Podman:

```bash
systemctl --user start podman.socket
DOCKER_HOST=unix:///run/user/$UID/podman/podman.sock TESTCONTAINERS_RYUK_DISABLED=true ./gradlew test
```

The S3 tests use `adobe/s3mock`, because the community MinIO images are no longer published.

### Tests that contact real websites do not run

They are tagged `network` and run only on request: `./gradlew test -Dinclude.network=true`.

### Playwright downloads another Chromium, or cannot find it

`@playwright/test` (frontend) is pinned to the same version as `playwright-java` (backend), 1.63, so that
both use the same Chromium build. Keep the two versions aligned when you upgrade.

### End-to-end tests cannot start their server

They build the frontend and serve it on port 3100. Free that port, or run them against a server that is
already started:

```bash
E2E_BASE_URL=http://localhost:3001 npm run test:e2e
```

This also lets you test against `next dev`, where React StrictMode is active.

## 8. Containers and deployment

### The worker container exits right after startup

Check the logs:

- **Read-only root filesystem**: the worker needs writable `/tmp` and `/home/pwuser` (tmpfs).
- **Chromium shared memory**: give Chromium enough shared memory (`shm_size: 1gb`).
- **Old image**: images built before the fix exited because no non-daemon thread was left. Rebuild them.

### `NoSuchBucket` or access errors on screenshots

The S3 bucket must exist before the start, and the credentials must allow `PutObject`, `GetObject`,
`HeadObject` and `DeleteObject`.

### HSTS is not sent / redirects use `http://`

Behind the reverse proxy:
- set `FORWARD_HEADERS_STRATEGY=framework` (already set in the `api` image);
- make the proxy send `X-Forwarded-Proto: https`.

## 9. Desktop application

### `Port 8081 already in use`

The all-in-one JAR starts its backend on 127.0.0.1:8081. Stop whatever process uses that port, for example
a backend started with `bootRun`.

### The Swing window shows no results

The window talks to `http://localhost:8081` (`client.properties`). Check that the backend started (console
output) and that nothing else answers on that port.

## 10. Where are the logs?

| Component | Logs |
|-----------|------|
| Backend (development, desktop) | Console of `./gradlew :backend:bootRun` or `java -jar` |
| Backend containers | Container standard output, JSON (ECS format) |
| Frontend (development) | Console of `npm run dev` |
| Keycloak | `docker logs <container>`; login errors are `type="LOGIN_ERROR"` events |
| Monitoring | `/actuator/health` and `/actuator/prometheus` on port 8082 (instances started with the `api` or `worker` profile) |
